RELAY — PROJECT STRUCTURE & HOW IT WORKS
=========================================
(Flutter app, package name `relay`, product-named "EBL Relay" in the shell
chrome/icon only — nothing else in the codebase renamed.)

WHAT IT IS
----------
Executive memo approvals for mobile: sign in, see a feed of memos waiting on
your sign-off, open one, approve / request revision / decline, manage a
sign-off proxy and app preferences in Settings. Built from a Figma design
("Logo STA"). 5 real screens — Welcome, Sign-in, Memos feed, Memo detail,
Settings — plus Modules/Activity tabs that are stubbed empty states (no Figma
frames for them).


1. HOW THE APP BOOTS
---------------------
  lib/main.dart
      -> calls bootstrap() and nothing else. Every build flavor (dev /
         staging / prod) goes through this one entry point.

  lib/bootstrap.dart
      1. WidgetsFlutterBinding.ensureInitialized()
      2. AppConfig.fromEnvironment() reads the --dart-define-from-file
         values compiled into the binary (APP_ENV, API_BASE_URL,
         USE_MOCK_BACKEND, ENABLE_LOGGING, PRIVACY_URL, HELPDESK_URL,
         TRUST_CENTER_URL) and VALIDATES them. Missing/invalid config
         throws ConfigurationException instead of starting with unsafe
         defaults ("fail closed"). If that happens, runApp shows a plain
         "Relay is not configured" screen and stops — this is why the app
         MUST be launched with a config file, e.g.
         `flutter run --dart-define-from-file=config/dev.json`.
      3. Installs global error handlers (FlutterError.onError,
         PlatformDispatcher.onError) that log but never leak stack traces
         into the release UI (release ErrorWidget is a neutral message).
      4. Loads SharedPreferences.
      5. runApp(ProviderScope(...RelayApp...)) with appConfigProvider and
         sharedPreferencesProvider overridden to the real instances — this
         is the one place the Riverpod graph gets its real inputs.

  lib/app/relay_app.dart (RelayApp, a ConsumerWidget)
      - Watches routerProvider and preferencesControllerProvider.
      - Builds MaterialApp.router with AppTheme.light()/dark(), themeMode
        driven by the user's Appearance preference (system/light/dark).
      - Wraps the tree in a status/nav-bar color matcher (_SystemBars) and a
        text-scale combiner (_TextScaleBoundary: OS scale x in-app preset,
        clamped 0.8x-2x) so both platform accessibility and the in-app
        "Standard/Large/Extra Large" setting apply together.

3. NAVIGATION
--------------
route_paths.dart: /splash, /welcome, /login, /memos (+ /memos/:memoId),
/modules, /activity, /settings.

app_router.dart builds one GoRouter with a `redirect` callback that is the
ENTIRE auth gate for the UI (not a security boundary — see section 7):

  sessionControllerProvider is AsyncLoading  -> force /splash
  sessionControllerProvider has no user      -> allow only /welcome,/login,
                                                 else send to /welcome
  sessionControllerProvider has a user       -> if on /welcome,/login or
                                                 /splash, send to /memos
  otherwise                                   -> no redirect

Routes:
  /splash                     SplashScreen (shown while the stored session
                                is being restored)
  /welcome                    WelcomeScreen — first screen an unauthenticated
                                user sees; its "Sign in" button does
                                context.push('/login')
  /login                      LoginScreen — the actual email/password (+
                                biometric quick-unlock, SSO) form
  StatefulShellRoute.indexedStack (MainShell, only reachable once signed in)
    /memos                    MemosFeedScreen
      /memos/:memoId           MemoDetailScreen — pushed on the ROOT
                                navigator (parentNavigatorKey), so it
                                covers the bottom nav like a full-screen
                                page; :memoId is validated with SafeId
                                before use (unknown/malformed id -> 404)
    /modules                  PlaceholderTabScreen (empty state)
    /activity                 PlaceholderTabScreen (empty state)
    /settings                 SettingsScreen

Each StatefulShellBranch keeps its own navigation stack + scroll offset via
IndexedStack, so switching tabs never rebuilds/reloads a screen.


4. THE PER-FEATURE LAYERING (Clean Architecture, feature-first)
------------------------------------------------------------------
Every feature folder (auth, memos, settings; onboarding has no logic of its
own) is split into three layers with a ONE-WAY dependency rule:

        presentation --> domain <-- data

`domain` imports no Flutter/Dio/storage code at all — it is pure Dart
business rules and types, so it is trivially unit-testable and does not care
whether the backend is real or mocked.

  domain/
    entities/        plain Dart model classes (UserProfile, MemoFeed,
                      MemoDetail, ApprovalDecision, SignOffProxy, ...)
    repositories/     ABSTRACT repository interfaces (e.g. MemoRepository)
                      — the contract `data/` must implement
    usecases/         one class per business action (SignInWithCredentials,
                      GetMemoFeed, SubmitMemoDecision, ...). This is where
                      RULES live, e.g.:
                        - a decline/revision note must be 3-500 characters
                        - the last active module in Settings can't be
                          turned off
                        - ids are validated before being used
                      Each usecase is a thin callable wrapping one
                      repository method plus its validation.

  data/
    dtos/             *Dto classes that parse a raw JSON map (via
                      JsonObject) into a typed, defensively-checked shape,
                      then convert to a domain entity. Money is parsed as
                      integer cents. Unknown optional enum values are
                      skipped rather than failing the whole payload;
                      malformed REQUIRED fields throw
                      MalformedResponseException.
    datasources/      two implementations per contract:
                        *_remote_data_source.dart  -> real HTTP calls via
                                                       the shared Dio
                        *_mock_data_source.dart    -> in-memory canned data
                                                       with simulated
                                                       latency, used when
                                                       USE_MOCK_BACKEND=true
    repositories/      *RepositoryImpl — implements the domain interface,
                      wraps every data-source call in `guardedCall(...)`
                      so nothing above this layer ever sees a raw
                      exception; always returns Result<T>.

  presentation/
    providers/        Riverpod wiring for this feature:
                        - a Provider building the data source (picks mock
                          vs. remote by reading appConfigProvider)
                        - a Provider building the repository
                        - a Provider per use case
                        - one or more Notifier/AsyncNotifier classes that
                          hold UI state and call use cases, converting
                          Result<T> into AsyncValue<T> (success) or
                          AsyncError (failure.message) for widgets to watch
    screens/           full-page widgets, composed from...
    widgets/           ...feature-specific presentational widgets (no
                      business logic — they call the controller and render
                      whatever state it reports)

Concrete example — the "approve a memo" flow, end to end:
  1. User taps Approve in memo_feed_card.dart or detail_content_cards.dart
  2. MemoDecisionFlow.approve() (memo_decision_flow.dart) shows a confirm
     dialog, then calls
     ref.read(memoDecisionControllerProvider.notifier).decide(...)
  3. MemoDecisionController (memo_providers.dart) calls the
     SubmitMemoDecision usecase, which calls MemoRepository.submitDecision,
     implemented by MemoRepositoryImpl, which calls the mock or remote
     MemoDataSource wrapped in guardedCall — an Idempotency-Key header
     (from SecureIdGenerator) prevents a double-tap from double-approving.
  4. The Result<void> comes back up through every layer unchanged.
  5. MemoDecisionFlow._report() turns Success into a green RelaySnackbar
     and Err into a red one showing failure.message (a fixed, user-safe
     string — never raw server/exception text, see failure.dart).
  6. memoFeedControllerProvider.autoDispose is invalidated so the feed
     re-fetches and the memo disappears from the pending list.

This Result -> AsyncValue -> widget pattern, and the
mock-vs-remote-by-config switch in each *_providers.dart, repeats
identically for auth (sign in / restore session / biometric unlock) and
settings (profile, sign-off proxy, preferences).


5. STATE MANAGEMENT & DEPENDENCY INJECTION
---------------------------------------------
Riverpod everywhere, no code generation (hand-written Provider /
NotifierProvider / AsyncNotifierProvider declarations).

  - core/providers/core_providers.dart is the composition root: it is the
    ONLY place that constructs environment-specific singletons (Dio,
    TokenStore, logger, etc.), and bootstrap.dart is the only place that
    overrides the two providers that need a real runtime instance
    (AppConfig, SharedPreferences).
  - Every feature's `*_providers.dart` builds its own graph on top of
    core_providers — datasource -> repository -> usecases -> controller.
  - Swapping mock vs. real backend is a single provider lookup
    (`ref.watch(appConfigProvider).useMockBackend`), never an if/else
    scattered through the UI.
  - Tests override providers (ProviderScope(overrides: [...])) instead of
    mocking globals — see test/helpers/test_harness.dart.


6. THEMING / DESIGN SYSTEM
------------------------------
  AppPalette (ThemeExtension)  - every semantic color, light + dark, read as
                                 `context.palette.background`,
                                 `context.palette.brand`, etc. No widget
                                 hardcodes a Color() literal for brand UI.
  AppTypography                - the full type scale as named TextStyle
                                 constants (titleAuth, headline, label14,
                                 caption, body styles, ...), colorless by
                                 default so the same style works in both
                                 themes; `context.text.xxx` gives the
                                 secondary-colored variants.
  AppMetrics (AppRadii/AppLayout/AppShadows) - every corner radius, layout
                                 constant and box-shadow recipe used in the
                                 app, pulled from the Figma export.
  AppTheme.light()/dark()      - assembles a Flutter ThemeData from the
                                 above, plus the RelayAccessibilityTheme
                                 extension (the "High Contrast Borders"
                                 setting, read by RelayCard/text fields to
                                 draw a visible border when on).
  core/widgets/*                - the shared component library screens are
                                 built out of (buttons, cards, pills, text
                                 fields, dialogs, snackbars, toggles, the
                                 SvgAsset icon wrapper with automatic dark-
                                 mode tinting via AppIcons.darkTones).

Fonts: Epilogue (headings/metrics) and Plus Jakarta Sans (everything else),
both bundled as variable fonts (OFL-licensed, no runtime font fetching).


7. ERROR HANDLING & SECURITY POSTURE
----------------------------------------
  - Failure (sealed class) + Result<T> (sealed success/err) + guardedCall
    together guarantee no raw exception or server error text ever reaches
    a widget; every UI surface gets a fixed, human-readable message.
  - The client is explicitly NOT a trust boundary: route guards in
    app_router.dart only decide which screens to SHOW. Every API call is
    still authorized server-side; a 401 triggers one silent refresh then
    signs the session out (auth_interceptor.dart + SessionEvents), a 403
    is surfaced and never bypassed.
  - AppConfig fails closed: invalid/missing config refuses to start rather
    than falling back to insecure defaults; the mock backend is only
    permitted when APP_ENV=dev; API_BASE_URL must be https with no
    embedded credentials or query string.
  - Tokens live only in Keychain/Keystore via SecureTokenStore, never in
    SharedPreferences.
  - Deep-link / path ids are allow-listed (SafeId) before use; free text is
    run through input_sanitizer.dart.
  - Idempotency-Key headers stop double-submits on sign-off actions;
    confirm dialogs gate every approval/decline; buttons lock while a
    request is in flight.
  See README.md's OWASP table for the full A01-A10 mapping.


8. CONFIGURATION
--------------------
Nothing is read from the environment at runtime — everything is compiled in
via `--dart-define-from-file=config/<env>.json`:

  config/dev.json       APP_ENV=dev,     USE_MOCK_BACKEND=true  (offline,
                          any email + 8+ char password signs in)
  config/staging.json    APP_ENV=staging, USE_MOCK_BACKEND=false (needs a
                          real https API_BASE_URL)
  config/prod.json       APP_ENV=prod,    USE_MOCK_BACKEND=false (mock is
                          refused outright by AppConfig.parse in prod)

config/*.local.json is git-ignored for private overrides. Run:
  flutter run --dart-define-from-file=config/dev.json

10. KNOWN GAPS (see README.md "Known gaps" for the full list)
------------------------------------------------------------------
  - Settings screen icons are Material stand-ins (Figma quota ran out
    before its design context was fetched); Marcus Brody avatar falls back
    to initials.
  - SSO reports "not available" until a tenant identity provider is wired
    up (SignInWithSso usecase exists but has no backend to call).
  - "Swipe to batch" and Search are present visually but have no specified
    behavior yet.
  - Offline outbox is a documented no-op — every write is online-only.
  - No certificate pinning, no localization, light theme design only (dark
    palette values are derived, not from Figma).
  - Android build is currently blocked locally by a JDK 8/17 mismatch (see
    the Claude memory notes on this machine for the exact fix).
